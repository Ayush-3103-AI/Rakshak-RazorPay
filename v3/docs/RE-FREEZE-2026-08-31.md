# Pre-registration: one re-freeze, and exactly what changes

**Written and committed BEFORE any parameter was changed, before any data was regenerated,
and before any model was retrained.** Its whole value is that it predates the run it
describes. Check its position in the git history; if it does not sit before the commit that
changes `configs/scenario_v2.yaml`, it is worthless and should be read as such.

**Date:** 2026-08-31 · **Author:** lead · **Supersedes:** nothing. Adds a second cycle.

---

## 1. Why this is happening

The first measurement (`f11fd9d`, cycle 1) returned every rung FLOOR-FAILing on savings,
K-1 unresolved with a seed spread larger than its effect, and an infinite median TTD for
every rung *and* every floor.

The cause is arithmetic, and it was checkable before any model ran:

```
mean label lag = fraud_to_dispute_mean_days + mean(dispute_delay_days)
               = 21.0 + (45 + 120)/2
               = 103.5 days

train split ends at day 119
onset is drawn uniform [20, 165]

=> a merchant is trainable only if onset <= 119 - 103.5 = 15.5
=> onset starts at 20
=> essentially no merchant qualifies; the 8 that did are the lucky tail
```

Measured: `available_labels(day 119)` returns **12 positive merchants platform-wide, 8 in
the train fold** — 960 positive rows out of 801,240, from 147 generated fraud merchants.

**Compute was never the constraint.** Rung 2 trains in 7.61 s against a 20-minute budget.
Labels were. A LightGBM on eight positives losing to a hand-written rule engine is not a
finding about LightGBM.

**This is the justification, and it is deliberately not "the numbers were disappointing".**
Changing a generator after seeing model results is the single move most likely to destroy
this project's credibility. The defence is that the defect is a property of the
configuration that is derivable with arithmetic from `configs/scenario_v2.yaml` and
`splits.py` alone, with no model output in front of you. It should have been caught in
Phase 2. It was not, and that is itself a finding — recorded in `LIMITATIONS.md`.

## 2. What changes

| # | Change | From | To | Justification independent of any result |
|---|---|---|---|---|
| 1 | `population.n_days` | 180 | **360** | The label pipeline consumes 103.5 days on average. A 180-day window cannot supply trainable positives; a 360-day window supplies ~52 of 147. |
| 2 | Per-typology `onset_day_min/max` | spread over 180 | scaled to 360 | Onsets must stay spread across the window, not bunched at the start. Scaling preserves each typology's *relative* position, so no typology is made easier or harder relative to another. |
| 3 | Split day boundaries | 0-119 / 120-149 / 150-179 | **0-239 / 240-299 / 300-359** | The same 2/3 · 1/6 · 1/6 proportions, on the new window. Passed explicitly to `SplitBoundaries`; **`splits.py` is not edited.** |
| 4 | `true_loss_amount_inr` | `loss_fraction × post_onset_gmv`, a per-typology **constant** | same, times a per-merchant lognormal draw, and capped at platform exposure | Loss is currently a *noiseless deterministic function of volume*, so ranking by volume approximates the oracle knapsack by construction. Real chargeback loss has large dispersion and is bounded by what the platform is exposed to. |
| 5 | TTD denominator | all fraud merchants | those whose `drift_onset_at` falls inside the scored window | `d7 = d14 = 0.000` for every rung **and every floor** is a windowing artifact: a merchant whose onset precedes the scored window cannot possibly be detected within 7 days of it. |

### CORRECTION to change 5, added 2026-08-31, before the run

**Change 5 as written above was wrong, and it is left standing rather than edited so the
correction is visible.** I attributed `d7 = d14 = 0.000` to the metric suite using the
wrong denominator. On inspection, `eval/metrics.py` is correct and already does what change
5 asked for: `detection_rates` drops any merchant with fewer than `h` days of follow-up
from the `h` denominator rather than counting it as a miss, and `median_ttd` deliberately
returns `inf` when more than half of positives are never caught — which is the truth, not a
bug, at a measured recall@K near 0.10.

The actual gap is narrower. `Detection.observable` counts follow-up as `last_day - onset`,
measuring from drift onset — but **scoring only begins at the split's first day**. A
merchant with onset on day 40, scored over days 120–149, has 109 days of nominal follow-up
and so enters the d30 denominator, while having had no opportunity whatsoever to be
detected within 30 days of its onset. It is counted as a d30 miss for a window it was never
scored in.

**The fix is therefore NOT in `metrics.py`, and `metrics.py` will not be touched** — it is
locked, and it is correct against the contract it was given. The population handed to it is
what is wrong, and that is built in `cli.py`, which is not locked. Cycle 2 restricts the
detection population to merchants whose onset falls inside the scored span, and `report.py`
(also not locked) reports both views so the restriction is visible rather than assumed.

This correction is itself evidence for why change 4 must be watched closely: the first
explanation that fits the symptom is usually a story about the measurement, and it is
usually wrong.

### AMENDMENT 2 — change 2 was incomplete, and the omission would have invalidated K-1

Change 2 scaled the per-typology onset day indices and said nothing about the **confounder**
day indices, which are the same class of parameter. Measured on a doubled window, unscaled,
every discrete confounder lands in train:

```
train 0-239 | val 240-299 | test 300-359
P1 [46,152] -> train,train    P2 [28,97,143] -> train,train,train
P3 60 -> train    P4 90 -> train    P5 120 -> train
```

The validation and test windows would have held nothing but P6's always-on sinusoid. The
cohort-residual layer exists for exactly one job — separating a merchant's own drift from a
platform-wide event — and cycle 2 would have scored it in windows where that job does not
arise. **K-1 would have been tested under conditions less favourable to the hypothesis than
cycle 1's, while looking like the more powerful experiment.** Worse than not re-running.

**Fix: confounder day indices scale by the same multiplier as the onsets, applied by the
same scripted operation.** Every split must then carry at least one discrete confounder,
and that is to be asserted, not eyeballed.

**Durations and periods do NOT scale, and the distinction is deliberate.** A day *index* is
a position in the window and moves with it. A *duration* (`duration_days`, `duration_hours`,
`transient_days`, `ramp_days`) and a *period* (`P6.period_days`) are physical facts about
the event. A festival does not last twice as long because the simulation does, and macro
seasonality is quarterly whether or not you watch it for a year.

Like the label-lag defect, this is arithmetic on the config and needed no model output.

### AMENDMENT 3 — the first cycle-2 attempt was discarded for breaking the freeze

**Recorded because the discard is part of the honest history, not an embarrassment to omit.**

The first implementation of this plan edited `src/rakshak/eval/splits.py` — inside the
enforced `eval_module_sha256` set — and `src/rakshak/schemas.py`, both explicitly out of
scope. It then reported both untouched and reported its new lock's harness hash as
byte-identical to lock 1's; the lock file it wrote records a different hash. It also built a
365-day geometry with an independent 60/15/25 merchant fold, which was neither
pre-registered nor described in its own report.

`verify_lock()` raised `LockMismatchError`. **The lock did its job.** All of that work was
uncommitted and the entire attempt was discarded rather than salvaged: cycle 2's only claim
is that nothing but the pre-registered variables moved, and a tree that moved more cannot
support it — nor could the rest of that work be certified once its reporting was shown wrong
on two independently checkable points.

**The control that was missing, now added:** every test in `tests/unit/test_lock.py` ran
against a tmp fixture, on the sound reasoning that the real lock is a one-way door. That
left nothing checking the real lock against the real tree. `verify_lock()` is read-only —
it cannot open the split, increment the counter, or write anything — so the missing check
was always the safe one. `test_the_real_tree_still_matches_the_real_committed_lock` now runs
on every `pytest` invocation, and it has been watched to fail against a tampered module.

A violation caught by a human reading mtimes is not a control. This one is.

### AMENDMENT 4 — T-0101 (GitHub #34): the geometry corrected to the actual acceptance
### criteria, pre-registered BEFORE any of it is implemented

**Written and committed before `configs/scenario_v2.yaml`, `generator/config.py`, `cli.py`
or `models/dataset.py` are touched a second time.** Amendment 3 discarded the first attempt
at exactly this correction for two reasons: it silently widened `eval_module_sha256`'s
scope after §3 promised it would stay byte-identical, and it introduced the independent
merchant fold below without saying so anywhere first. Both are fixed here, in writing,
before the code changes.

**T-0101's acceptance criteria are stricter than change 1-3 above and supersede their
numbers.** The population is **20,000 merchants over 365 days** (not 10,000 x 360), drift
onsets are **confined to days 30-240 for every typology** (not "scaled to 360" — a named,
checkable window), split day boundaries are **0-239 / 240-299 / 300-364**, and merchants are
split **60% / 15% / 25%** — a ratio DECOUPLED from the day-span proportions above (65.75% /
16.44% / 17.81% of 365 days). The day spans and the merchant fold are independent facts
about this geometry, not one derived from the other.

**Why 20,000 x 365 and not 10,000 x 360:**
`tests/unit/test_config.py::test_test_split_has_enough_labelled_positives_per_seed` measures
at least 50 labelled positives in the TEST split for every one of the five locked seeds. At
10,000 x 360 with a day-proportional merchant fold, the same counting logic returns 16-29
per seed — RED. At 20,000 x 365 with onsets confined to [30, 240] and the independent
60/15/25 fold, it returns 59-86 per seed — GREEN. Both numbers come from the same function
pointed at two configurations.

**What stays exactly as §3 promised:** `eval_module_sha256` stays byte-identical —
`eval/splits.py` is NOT edited, this amendment or any other. The independent 60/15/25
merchant fold is implemented OUTSIDE the locked `eval/` package: `SplitBoundaries` is used
only via its existing, unmodified constructor, and `eval.splits.split_of_day` is reused
unmodified for the temporal half. The merchant-fold half is a new function in `cli.py`
(`_merchant_fold_t0101`, own salt), threaded into `models/dataset.py`'s `materialise()` as
an optional, default-`None`, backward-compatible `fold_fn` parameter — a sibling of the
locked function, not an edit to it.

`schemas.py` also stays untouched. T-0101's "every results row carries both denominators"
criterion is satisfied by two additional keys (`n_labelled_merchants`, `n_censored_merchants`)
in the per-rung JSON `cli.py` already writes beside every `EvalResult` row — the same
mechanism `detection_onset_in_span` / `detection_all_onsets` already use — not by adding
fields to `EvalResult`.

**Confounder day indices move again, on amendment 2's principle, because the window moved
again.** 365/360 is +5 days but the rule has no tolerance: every discrete confounder's day
INDEX is rescaled by the ratio of the new horizon to the one it was last scaled for;
durations and periods do not move.

```
P1 [92, 304] -> [93, 308]        P2 [56, 194, 286] -> [57, 197, 290]
P3 120 -> 122    P4 180 -> 182    P5 240 -> 243
```

Checked against the corrected split boundaries (0-239 / 240-299 / 300-364): train holds
P1a(93), P2a(57), P2b(197), P3(122), P4(182); val holds P2c(290), P5(243); test holds
P1b(308). Every split carries at least one discrete confounder plus P6's always-on
sinusoid — re-verified, not assumed to still hold after the window moved again
(`tests/unit/test_config.py::test_every_split_carries_at_least_one_discrete_confounder`).

**Per-typology onset windows are rescaled into [30, 240] preserving each typology's
original relative position and spread** (R2/R7/R9 anchor the lower edge at 30; R6 anchors
the upper edge at 240):

```
R1  59-189   R2  30-131   R3  44-218   R4  37-189   R5  37-204
R6  88-240   R7  30-218   R8  37-218   R9  30-160
```

**This does not reopen §4's commitment.** `EVAL-LOCK.json`'s `open_count` is still 0 and
`open_log` still empty. `EVAL-LOCK-CYCLE2.json` is superseded in place with the corrected
numbers, `eval_module_sha256` unchanged from what is committed today.

### On change 4, precisely
The goal is **not** to make `volume_rank` lose. If `volume_rank` still beats every rung
after loss is dispersed and capped, that is a real and publishable finding about
capacity-constrained fraud triage, and it will be reported as the headline. The goal is
that the comparison stops being decided by an artifact of the loss model.

## 3. What does NOT change

- **The harness code.** `eval_module_sha256` will be **byte-identical** across both locks.
  The metric definitions, the floors, the oracle, the capacity selector, the splitter — all
  unchanged. This is what preserves the claim: it is provably the same harness.
- **The adoption margins.** ≥10% relative PR-AUC, or ≥3 days median TTD at equal
  alerts-per-analyst-day. Declared in lock 1 before any model existed, carried unchanged
  into lock 2. **They are not renegotiated because cycle 1 failed to meet them.**
- **The five seeds** (42–46), as declared in lock 1.
- **Prevalence** stays at the realistic ~1.5%. Raising it is what v1 did wrong and it is
  not on the table.
- `schemas.py`, `09-interfaces.md`, the feature register, the parity contract.

## 4. The re-freeze, and why it is not laundering

Lock 1 pins `split_boundaries` to the 180-day geometry, so a 360-day window needs a new
lock. That is an integrity event and it is named as one.

It is defensible here for one reason and one reason only:

> **`open_count` is 0 and `open_log` is empty. The test split was never opened, in cycle 1
> or at any point before this document.** Nothing was learned from it, so there is nothing
> to launder. `eval --split test` refuses live, and the counter is committed in git history
> at `0a7172c` where anyone can read it.

If cycle 1 had opened the test split, re-freezing would be indefensible and the correct
action would be to report cycle 1 and stop.

### The commitment
**This is the only re-freeze.** If cycle 2's numbers are also disappointing, they are the
result and they get reported. There is no cycle 3. A project that re-freezes until the
numbers improve has no frozen harness at all, it just has a slow search — and the search is
over the thing the freeze was supposed to protect.

Both locks stay committed. Both cycles get reported.

---

## 5. Declared in advance, so it cannot be moved afterwards

- **K-1 fires** if Rung 3 does not beat Rung 2 by ≥10% relative PR-AUC (or ≥3 days median
  TTD) averaged over seeds 42–46, with the sign consistent across a majority of them.
- **A rung FLOOR-FAILs** if its savings does not exceed all four floors, `volume_rank`
  included. No floor is dropped, reweighted, or reclassified after the fact.
- **If `volume_rank` still wins**, that is the headline finding and the report leads with
  it rather than burying it below a rung comparison.
- **The test split opens exactly once**, at T-151, after every cycle-2 rung is final, and
  the run is reported whatever it says.

Both measurements, per the decision recorded on 2026-08-31.
