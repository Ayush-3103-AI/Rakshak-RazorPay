## Dependency deviation, taken deliberately

The board lists T-120 as `Depends on: T-102, T-112`. T-102 is done; **T-112 was still in
flight in Lane A when this ticket started**, so the suites here are built against
`synthetic_stream` from `tests/parity/conftest.py` rather than against real persona output.
The dependency is narrow and this is a fair substitute: the features depend only on the
frozen `schemas.py` and `spec.py`, and `synthetic_stream` already carries the four shapes a
feature has to survive — empty days, a merchant with no events at all, refunds interleaved
with captures, and failed transactions.

**The tier suites should be re-run against real generator output once T-112 lands.** Two
things will only be exercised then: instrument variety (`i_intl_share` and `i_cnp_share`
see one instrument and one flag value in the synthetic stream, so their parity is real but
their range is not), and long dormancy (the synthetic stream's gaps are days, and
`v_dormant_burst` is built for weeks).

Not split into T-120a/b/c: the family groups turned out to share one base class and one
state object, so splitting would have meant three tickets each re-deriving the same day
roll. Recorded here in place of the split the board offered.

The design that made it fit in one session is **the fixed-calendar-day warmup window**.
Each feature's baseline is the merchant's first `warmup_days` calendar days, empty days
included, and the *denominator is a compile-time constant*. That is what makes the online
form O(1): a day with no events contributes 0 to the sum and 0 to the sum of squares, so
the online runner never has to reconcile empty days it never saw. A baseline over "active
days" would have been cheaper still and wrong — offline knows which days were empty and
online does not, so the two would have disagreed for exactly the sparse merchants that
matter.

z is **0.0 until the window has elapsed**, not shrunk, not computed from a partial window.
The cold-start problem is T-121's, solved once in the cohort layer, rather than solved
badly twice.

`warmup_days` is constructor configuration rather than a class constant, so the parity
suite runs every feature twice: once at a 5-day window over the 21-day stream (which
exercises the z arithmetic) and once at the production 30-day window over a 90-day stream
(which exercises the freeze). A suite that only ran the second would have been green while
asserting that every z-feature returns 0.0.

## Surprised

**`spec.py`'s guard against intermediate abstract bases never fires.** It reads
`getattr(cls, "__abstractmethods__", None)` inside `__init_subclass__` — but `ABCMeta` sets
`__abstractmethods__` *after* `type.__new__` returns, and `__init_subclass__` runs *during*
it. The attribute is a type slot and is not inherited through the MRO, so it is always
absent at that moment and every abstract base is treated as a concrete feature. This is
invisible in T-102 because the reference feature has no abstract base under it; the first
abstract base in the repo hit it immediately. Worked around with placeholder class
attributes on `Tier1Spec` and `StaticSpec`. The real fix is one line in the frozen file —
`if inspect.isabstract(cls): return` **after** class creation, or a check on
`cls.__dict__`'s unimplemented methods — and it is the lead's to make.

**`pl.lit(1.0).sum()` inside a `group_by` is 1.0, not the group size.** A scalar literal is
not broadcast to the group's height, so `_ONE` as a sentinel contribution produced a daily
transaction count of exactly 1.0 for every merchant on every day. It was the first parity
failure of the ticket and it is a good one: the online runner was right, the offline runner
was quietly answering a different question, and the harness caught it on day 6 of a 21-day
stream rather than in a model that mysteriously would not learn. Both sentinels are now
anchored to a non-null column so they are row-shaped.

**The register's state figures are not achievable, and the arithmetic was never done.**
`v_declared_ratio` is allotted 16 B for a *trailing-30-day GMV sum*. A sliding window has
to hold its values in order to evict them; 30 days of float64 is 240 B and there is no
cheaper exact form. Same for `v_fano_trailing` at 40 B for a 28-day Fano and `v_gmv_accel`
at 32 B for a three-week second difference. Honest declarations put T1 at **1720 B against
the ticket's 1024 bar**, and the overage is almost exactly the six private rings:
`v_gmv_accel` (21d GMV), `v_declared_ratio` (30d GMV), `h_weekend_share_z` (7d GMV),
`v_fano_trailing` (28d counts), `d_refund_amount_ratio` (7d amounts), `h_interarrival_cv`
(7d gaps) — three of which are rings over *the same daily GMV series*, kept three times
because `MerchantState.feature_states` is keyed per feature and there is nowhere else to
put shared state.

The fix is architectural and not a smaller number: **one shared per-merchant daily ring on
`MerchantState`** that every window feature reads. That needs a slot in the frozen
`state.py`. The budget test is left as `xfail(strict=True)` with the whole argument in its
`reason`, so landing the shared ring turns it red and forces `07-feature-register.md` to be
corrected rather than quietly outgrown.

**Measured state is 3.3× the declaration, and it is pickle's fault, not the features'.**
A full T1 `MerchantState` for the busiest merchant serializes to **7091 B against NFR-04's
4096**, while declaring 1720. The gap is ~120 B of pickle framing per `FeatureState`
object, times 24 objects. Declaring 120 B more per feature would be dishonest bookkeeping
for a cost that has nothing to do with the feature; the real answer is that
`MerchantState.nbytes()` should serialize to a packed array rather than to pickle. Flagged
for T-150, which is where the perf assertion lives.

**Three F1 features never needed the same window twice, and one needed a different z.**
`h_weekend_share_z` cannot be a Welford z: a daily weekend-GMV share is 0 on five days a
week by construction, so its "baseline" would be a distribution of mostly zeros and its z
would fire every Saturday for every merchant on the platform. It is a binomial-proportion z
instead — trailing-7d share against the merchant's pooled warmup share, over the closed-form
standard error. That is a small thing that would have been a silent, permanent,
platform-wide false positive.

## Broke

- `fill_null(0.0)` over a frame carrying a `Date` column raises. Every offline runner now
  fills only the numeric columns it means to.
- The `t_p95_median_ratio` P² estimator specified in the register was abandoned before it
  was written. P² is order-dependent by construction, so its offline twin would have to be
  a Python replay of the same recurrence — which is not an offline runner, it is the online
  one in a costume, and the parity test over it would be vacuous. Replaced with a 32-bin
  log histogram: same order of magnitude of state, exactly reproducible from a `group_by`,
  costs one bin of quantile resolution. Same histogram is reused by T-122's
  `t_wasserstein_7d`.
- `p_mcc_group` is a CRC32 bucket, not the one-hot the register asks for. One-hot needs a
  vocabulary and the vocabulary lives in the generator's config, which did not exist when
  this was written. CRC32 is stable across processes and platforms where `hash()` is not.
  The model layer can widen it once T-112's vocabulary is real.

## Could not build — reported, not worked around

**F8 (`s_payout_freq_z`, `s_balance_drawdown`) is not implementable under the frozen
interface.** `FeatureSpec.update(state, event: Transaction)` takes a `Transaction` and
`assert_parity(spec, txns, profiles)` carries no payouts, so a `Payout` cannot reach the
feature layer by any path. This is not a difficulty, it is an absence: the register calls
payout urgency "one of the strongest real-world bust-out tells and it costs almost
nothing", and it costs nothing only if the event stream carries it.

The change needed, in the frozen `spec.py` and `tests/parity/conftest.py`:

```python
def update(self, state: FeatureState, event: Transaction | Payout) -> None: ...
def assert_parity(spec, txns, profiles, payouts=()) -> None: ...
```

Not made here. Lane A and the lead both depend on `conftest.py`'s current behaviour and
`spec.py` is frozen; a lane that unfreezes an interface unilaterally is how parallel lanes
stop being parallel.

**A second, smaller interface gap, worked around rather than blocked on.**
`FeatureSpec.batch(frame, as_of)` receives transactions and nothing else, so no offline
runner can reach `MerchantProfile` — which every warmup window start, `v_declared_ratio`'s
denominator and all six F9 statics need. The online runner *can* reach it, because
`state_of` receives the whole `MerchantState`; each feature snapshots what it needs at
first touch. The offline half is closed by `tier1.PROFILES`, a module-level reference table
loaded once per run (`load_profiles`). It is reference data known at onboarding and
constant thereafter — the same table a real deployment holds in memory — not mutable state
and not an RNG. The honest fix is `batch(frame, as_of, profiles)` in `spec.py`.
