# T-102 — FeatureSpec dual-runner framework and the parity test harness

**Status:** done · **Session:** 2026-08-31

## Built
- `features/spec.py` — the `FeatureSpec` ABC. Four methods (`init_state`, `update`, `value`,
  `batch`) and five class-level declarations, validated in `__init_subclass__` so a feature
  missing its `state_bytes` or `human_template` fails at class creation rather than at
  registration.
- `features/state.py` — `MerchantState`, `BaselineStats` (Welford, **frozen after warmup**),
  and the `FeatureState` base. The freeze is the anti-R2 design choice, and should be named as
  such in the writeup: a rolling baseline lets a slow-ramp adversary walk the baseline along
  with it, so the merchant reads as permanently "normal relative to last month" while last
  month keeps getting worse.
- `features/registry.py` — `REGISTRY`, `ORDER`, `register()`. Sums declared `state_bytes` on
  every registration and raises `StateBudgetExceeded` past NFR-04's 4096, unwinding the failed
  registration first so a caught exception cannot leave a half-registered registry that the
  next import treats as valid.
- `tests/parity/conftest.py` — `assert_parity()`, generator-agnostic. Replays a stream through
  `update()` and compares against `batch()` **at every epoch for every merchant**, not at the
  final epoch and not on average.
- `tests/parity/test_reference_feature.py` — 14 cases.

## Surprised
**The parity harness needed its own tests more than the reference feature did.** A harness
nobody has watched fail is a harness nobody should trust, so the suite contains three
deliberately broken features — `LeakyBatch` (offline ignores `as_of` and counts the whole
history), `StaleOnline` (returns yesterday's count on an empty day), and `OffByOne` (a 1e-6
bias, invisible by eye and a thousand times the tolerance) — and the harness must catch all
three. It does.

**`value()` takes `as_of`, which is not obvious from the register.** Several features are
functions of elapsed time as well as of events: days-since-last-transaction keeps rising on a
day with nothing in it. A runner that only moved on events would report stale values for
exactly the dormant merchants that `v_dormant_burst` exists to catch. The reference feature
returns 0.0 rather than yesterday's count for the same reason, and `StaleOnline` is the test
that says so.

**`synthetic_stream` deliberately contains a merchant that never transacts.** It is absent from
every offline frame, so `assert_parity` has to define what "no rows offline" means — 0.0,
matching the online contract — rather than skipping the merchant. Skipping it would have left
the silent-merchant case untested, and that is exactly where a division by a zero count lives.
`test_the_stream_fixture_contains_the_awkward_cases` locks the edges in so the parity suite
cannot quietly get easier later.
