## Surprised
**Two real bugs, both invisible to an example-based test, both found by the property suite.**

1. **duckdb renders `TIMESTAMPTZ` in the session timezone**, which defaults to the machine's.
   On this laptop that is `Asia/Calcutta`, so the store handed back
   `Datetime("us", "Asia/Calcutta")` and comparisons against a UTC literal raised. The
   dangerous version is the one that does *not* raise and silently compares wall-clock times
   5.5 hours apart. Fixed by `SET TimeZone='UTC'` on the connection plus
   `_as_contract_dtypes()`, which casts every returned timestamp column back to the contract
   dtype at the single point duckdb hands data back.
2. **Windows ships no system tz database**, so `zoneinfo` cannot resolve even `"UTC"` and every
   tz-aware polars `Datetime` raised `ZoneInfoNotFoundError`. Added `tzdata>=2024.1` to the
   pins — a genuine dependency, justified here per CLAUDE.md.

**Linux CI would have caught neither.** It has the system tzdb and a UTC session clock, so it
would have stayed green while the machine doing the actual building was wrong. The pattern in
both: the tz-aware-UTC-nanosecond convention in 09-interfaces.md is not self-enforcing. It
needed a coercion point and a pin, or it would have held on whichever OS happened to run last.

## Broke
First full run: 6 failures, all from the two causes above. After the fix, 56 pass. The suite
ran 134s initially — duckdb does a full parquet scan per hypothesis example — so `max_examples`
came down from 200/100/50 to 60/40/25 and the suite is 14s. The properties do not need hundreds
of draws; they need draws at the boundaries, which is what the strategy already provides.
