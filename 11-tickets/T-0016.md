# T-0016 — Re-ground the generator on empirical marginals + fix the sampling design

**Day: unscheduled and CONDITIONAL — gated on T-0015's diff, see amendment** · **Risk:** **high — invalidates every existing number** · **Cuttable: yes, and expected to be cut** · **Depends on (blocked by):** T-0015, T-0003b

## Why this ticket exists

Two separate problems, both in the generator, both surfaced by measurement rather than opinion:

1. **Realism.** The generator's distributions were chosen by hand. T-0015 produces a calibration
   profile derived from real data; this ticket makes the generator honour it, so the synthetic
   marginals stop being assertions and start being fitted quantities.
2. **Sampling design.** The current design actively handicaps the model, measurably:
   - `FRAUD_MERCHANT_RATE = 0.20` — an order of magnitude above reality, chosen for per-class
     sample size, and it makes every precision number quotable only against its own prevalence.
   - **T-0004b's measured finding:** per-segment fitting scores 0.021 vs 0.091 pooled, because
     ~24 merchants per segment contain roughly 2 that are ever non-healthy. EM has almost no
     minority mass to learn from. This is a sampling defect, not a model defect.
   - 500 merchants × 39 windows is thin for a 4-state model with a 3.4% state.

## Build — `src/rakshak/generator/`

- **Consume `results/calibration_profile.json`.** Fit amount distributions, inter-arrival times,
  hour-of-day and day-of-week seasonality, and refund/chargeback base rates to the empirical
  profile. Where the profile cannot inform a parameter, keep the current hand-chosen value and
  **mark it in code as uncalibrated** — the distinction must be visible, not averaged away.
- **Separate training prevalence from evaluation prevalence.** These are different quantities and
  conflating them is the current design's core error:
  - training may oversample rare states, so the estimator gets minority mass
  - **evaluation must run at realistic prevalence**, or every precision number is unreadable
  - carry sampling weights through so metrics can be reweighted back to the true base rate, and
    make the harness report which prevalence each number was computed at
- **Stratified sampling of rare states** so each segment carries enough non-healthy merchants to
  fit, targeting T-0004b's 0.021-vs-0.091 finding directly.
- **Scale the population** as far as the 15-minute `make eval` budget allows. Measure the budget;
  do not guess it. Report the wall clock.
- Everything stays seeded and deterministic.

## What this ticket must NOT do

- **Do not touch RAMP's separability, duration, or amplitude, and do not soften SLOW_RAMP.**
  T-0004b's falsification test already measured 2× ramp amplitude: RAMP separation 1.19σ → 1.95σ
  but AMI went *down*. Ramp amplitude is not the binding constraint, so changing it buys nothing
  and would look exactly like tuning the generator until the gate passes.
- Do not re-run this ticket until a metric improves. Calibration is justified by fidelity to the
  profile, never by its effect on any score. If a calibrated generator makes results *worse*,
  that is the honest result and it ships.

## Done when

- Generator reproduces the T-0015 profile's marginals within a stated tolerance, tested
- Uncalibrated parameters explicitly marked in code and listed in the README
- Training and evaluation prevalence are separately configurable; evaluation defaults to the
  realistic rate; the harness reports which was used for every number
- Every existing test still passes, or its expected values are updated **with the old and new
  numbers both recorded** in `LOGBOOK.md`
- Determinism holds (NFR-003); `make eval` still inside 15 minutes, measured
- **A full re-measurement is published**: every headline number in `results/` regenerated on the
  recalibrated generator, with the pre-recalibration values beside them.

## The cost of this ticket, stated plainly

**It invalidates every number measured to date** — the K1 analysis, the 0.404 oracle ceiling,
T-0006's baseline table, T-0004b's per-item deltas. All of it must be re-run and re-reported.
That is not a reason to skip it; it is a reason to sequence it deliberately rather than drift
into it. If it lands after the code freeze, the correct outcome is to ship the current numbers
with the calibration gap documented as a limitation.

## Sequencing note (applies to T-0015 and T-0016 both)

These were raised on 2026-08-28, after T-0006, with the build window ending **Mon 1 Sep** and two
things already ahead of them: T-0007 (the cost matrix, currently making the primary `savings`
metric unreadable) and the K1 remediation reporting. Together T-0015 + T-0016 are roughly a
day's work and they force a full re-measurement.

Honest assessment: **this is the right idea at a difficult time.** It attacks the project's
single deepest limitation — that Rakshak has been measured only against a benchmark it wrote
itself. It is also the largest scope addition available this late. Recommended order is
T-0007 first (it unblocks the primary metric), then these. If they cannot land before the
freeze, ship with the limitation documented rather than half-recalibrated — a partially
recalibrated generator is worse than an honestly uncalibrated one, because the results table
would then be measured on a distribution nobody can characterise.

## Amendment — 2026-08-28, added during the post-T-0006 spec revision

### This ticket is now conditional, and its own evidence may answer "no"

It is no longer scheduled work awaiting a slot. It is **gated on T-0015's
`results/calibration_gap.md`** — the per-marginal diff between the empirical profile and
the generator's hand-chosen values:

- **divergence small** → the recalibration is a cheap parameter swap and the forced
  re-measurement is fast. Take it, if slack survives after T-0013.
- **divergence large** → publish `calibration_gap.md` as the stated limitation and **do
  not run this ticket.** This is not a concession; it follows from this file's own
  argument that a partially recalibrated generator is worse than an honestly uncalibrated
  one, because the results table would then be measured on a distribution nobody can
  characterise.

Either branch ships a committed artifact. The gap stops being an admission and becomes a
measurement.

### Realistic assessment of whether it lands

**It probably does not.** The queue ahead of it — T-0017, T-0006b, T-0007a, T-0007b,
T-0015, T-0012, T-0011, T-0013 — consumes the four remaining build days with no float,
and T-0012 took the last contested slot because validating on real data beats simulating
real data better. Recording that here so nobody later reads this ticket's absence as an
oversight. It was sequenced deliberately and lost on the merits of a stated comparison.

### Why T-0012 was preferred

T-0012 puts the decision layer on real bank data — the only point in the repo where a
model touches anything real. This ticket leaves everything synthetic, just synthetic with
better-sourced parameters, while invalidating the K1 analysis, the 0.404 oracle ceiling
and every baseline row on the final day before freeze.
