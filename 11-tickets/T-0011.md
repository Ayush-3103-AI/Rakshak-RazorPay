### Narrowed: the detection-lag probe

The board's open question asks whether LightGBM's −1.0 day median lag is legitimate early
warning or the generator telegraphing typologies before the state path records it. Reading
`generator/generate.py` narrows this considerably before any code runs:

`_ramp()` returns `lo` for **every day before `start`**, and every injector writes its
effect through `_ramp` or through an explicit `[onset:]` slice. No injector writes signal
ahead of the labelled onset. Meanwhile `WINDOW_DAYS = 7`, so a window straddling onset
contains up to 6 post-onset days — and a lag measured window-start-against-onset-day
yields exactly −1.

So the probe is now: **confirm window aliasing, rather than hunt for leakage.**

- Compute lag against first entry into any bad state, as originally required
- Recompute lag using the window's **last** day rather than its start, and check whether
  the −1.0 disappears. If it does, the finding is an aliasing artifact of the reporting
  convention; fix the convention and report both numbers
- Only if it does **not** disappear does the pre-onset separability probe become a
  leakage investigation. Run it either way — it is cheap and it clears the existing
  numbers, which matters because those numbers are what the README quotes
