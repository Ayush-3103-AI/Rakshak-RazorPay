## Build — `src/rakshak/models/hmm_score.py`

Register `score_hmm` conforming to the existing scorer contract:

    def score_hmm(split: Split, rng: np.random.Generator) -> pd.Series | pd.DataFrame

- **Fit on train only.** Use T-0004b's shipping configuration — partially-supervised
  fitting, items 1+2, pooled rather than per-segment. `STATE.md` records why per-segment
  fitting scores 0.021 against 0.091 pooled.
- **Score with the forward-only filtered posterior.** Per-merchant risk is derived from
  `P(merchant is in a bad state)` — bad states are `DORMANT`, `FRAUD`, `RAMP`, matching
  `results/summary.md`'s definition.
- **Return a `flag_day`** so median detection lag is computable. Models returning a bare
  per-merchant score read `n/a` on lag, which would waste the HMM's main advantage over
  gbdt.

### The constraint this ticket exists to get right

**`flag_day` MUST come from the forward-only filtered posterior. Never forward–backward.**

A smoothed posterior at window *t* conditions on windows after *t*. Using it to decide
when the model "first flagged" means deciding with information from the future — and it
would silently manufacture exactly the kind of negative detection lag already under
investigation for gbdt (`STATE.md`, open questions). This is the single most likely
methodological hole a panel member would probe, and the difference between `forward()`
and `posterior()` is one call site.

Add a test that asserts the flag decision at window *t* is unchanged when windows after
*t* are truncated away. That test is the proof, not the comment.

The *risk score* used for ranking may legitimately use the smoothed posterior — ranking
at end-of-window is not a temporal claim. If both are computed, name them distinctly and
say in the docstring which one feeds which metric.
