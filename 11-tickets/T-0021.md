# T-0021 — Verify `make eval` on a clean checkout

**Day:** Sun 30 Aug (first pass) · **re-run after the Tue 1 Sep freeze** · **Risk: the only remaining ticket that can fail and generate real work** · **Cuttable: no** · **Depends on (blocked by):** **T-0020** (it changes packaging); re-run after **T-0013**

## Why this ticket exists

`CLAUDE.md`: *"Every number in the README and the video must be regenerable by `make eval` with fixed seeds."*

**That claim has never been tested.** `make` is not installed on the build machine; `make.ps1` is a local PowerShell shim written to work around its absence. **The `Makefile` has shipped unexercised since T-0001.** `STATE.md` already carries the standing instruction: *do not claim `make eval` is green on camera until it runs on a Linux checkout.*

T-0019's script says the numbers regenerate. This ticket is what makes that sentence true rather than hopeful — and it is deliberately **not** bundled into T-0020, because every item there is a two-minute file edit that cannot fail, and this one can.

## Build

- **Clone the repo fresh**, into a directory with no build artifacts, no `data/`, no `results/`, no virtualenv, no `__pycache__`. A `git clean` on the working tree is **not** a substitute — it will not catch a file that is required but git-ignored.
- Run `make setup`, then `make eval`, then `make test`, then `make figures`, in that order, on a Linux checkout.
- Record wall-clock for `make eval` against **NFR-004's 15-minute budget** (K3).
- Diff the regenerated `results/` against the committed artifacts. They must match **byte for byte** at the same seed.

## The parts most likely to break, in order

1. **Generated inputs.** `make eval` reads a parquet the generator writes. On a clean checkout `data/` is empty and git-ignored — does `eval` generate what it needs, or does it assume a previous run? This is the most likely failure and the one that would embarrass the video.
2. **The BAF step.** `make eval` chains `rakshak.eval.baf`, which needs a 558 MB git-ignored download and a Kaggle credential. The Makefile tolerates its absence deliberately — **confirm the tolerated-failure path prints something a stranger can act on**, and that `make eval` still completes.
3. **Line endings and paths.** Everything was authored on Windows; `newline="\n"` is set explicitly in the writers. Confirm the byte-identical claim survives a Linux checkout.
4. **`make.ps1` drift.** The shim and the `Makefile` are two hand-maintained lists of the same commands. Confirm they still agree — `baf` was added to both on 2026-08-29.

## Done when

- `make setup && make eval && make test && make figures` all succeed on a **fresh Linux clone**
- `make eval` wall-clock is recorded and inside 15 minutes (NFR-004, K3)
- Regenerated `results/` artifacts are byte-identical to the committed ones at seed 42
- The BAF step's absent-data path is confirmed to fail tolerably with an actionable message
- `Makefile` and `make.ps1` are confirmed to expose the same targets
- **Re-run once after the Tue 1 Sep freeze**, on the frozen commit, and the result recorded in `LOGBOOK.md`

## If it fails

**Fix the Makefile, not the claim.** If `make eval` cannot regenerate the numbers on a clean checkout, then the README's provenance statement and T-0019's script are both false, and that is a bigger problem than whatever the fix costs. Raise it immediately — this is the one remaining ticket whose failure changes what the submission is allowed to say.
