# T-0022b — Harness data-path seam

**Day:** Sun 30 Aug (evening) → Mon 31 Aug · **Risk:** low, mechanical · **Cuttable: yes — ranks below T-0013/T-0018/T-0020/T-0021/T-0019, see BOARD.md cut order** · **Depends on (blocked by):** none — can start immediately, parallel to T-0022a

## Context to read

`project-context/14-spec-blackswan-and-drift-survey.md`. `src/rakshak/eval/splits.py`'s `load_split()`. `src/rakshak/eval/harness.py`'s `run()` (already takes a `results_dir` override — this ticket adds the matching data-path override).

## Why this ticket exists

T-0022c needs to score a second dataset (`data/synthetic_shock/`) through the exact same fitting/scoring logic that produced every existing number, so that a bug fixed once is fixed for both tracks and the shock track can never silently diverge from the primary scoring code. Today `load_split()` hardcodes `TRANSACTIONS_PARQUET` / `STATE_PATHS_PARQUET` from `config.py`.

## Build

- Add optional `transactions_path=` / `state_paths_path=` parameters to `load_split()`, defaulting to the current `TRANSACTIONS_PARQUET` / `STATE_PATHS_PARQUET` constants so every existing call site is unaffected.
- Add a matching optional pass-through to `harness.run()` (alongside its existing `results_dir` override).
- Do not reimplement any fitting or scoring logic — the same `evaluate_model` / `MODEL_REGISTRY` path must run regardless of which dataset it's pointed at.

## Done when

- `load_split()` and `harness.run()` accept the new overrides; calling either with no arguments behaves exactly as before.
- Regression test: `harness.run(seed=42)` with **no overrides** produces a `summary.md` byte-identical to the current committed one — proves this seam is inert on the primary path.
- A second test runs `harness.run()` pointed at an arbitrary alternate parquet pair (a copy of the real data is sufficient for this ticket — T-0022c is what points it at the real shocked dataset) and confirms it scores successfully.
- `python -m pytest` and `python -m ruff check src tests` still pass.

## What this ticket must NOT do

- Must not change any default behavior of `load_split()` or `harness.run()`.
- Must not touch `MODEL_REGISTRY`, `evaluate_model`, or any model-fitting code.
- Must not itself generate or reference `data/synthetic_shock/` — that's T-0022a's and T-0022c's job.

## Amendment — 2026-08-30, before implementation

**The Build list above was incomplete.** `load_split()` is not the only place a dataset is
read. Tracing the seam end to end found four more:

| Where | What it does | In the original Build list |
|---|---|---|
| `splits.py:248-250` | `load_split` reads the two parquets | yes |
| `splits.py:342` | `split_summary()` reads `STATE_PATHS_PARQUET` — the harness prints this table | no |
| `gbdt.py:138` | `build_window_matrix` reads `STATE_PATHS_PARQUET` for window labels | no |
| `gbdt.py:210-212` | `fit()` calls `load_split("train")` / `load_split("validate")` internally | no |
| `hmm_score.py:227` | `fit()` calls `load_split("train")` | no |
| `hmm_score.py:235` | `fit()` reads `STATE_PATHS_PARQUET` directly for its training labels | no |

**Consequence if built exactly as written.** `harness.run(transactions_path=shock)` would score
on `data/synthetic_shock/` while `gbdt` and `hmm` *train* on `data/synthetic/`. Silent
cross-dataset contamination, no test catching it, and `results/blackswan.md` reading plausible
and being wrong. `random` and `rules` are stateless (`rules.py:174`), so only the two fitted
models are affected — which is worse, not better: those are the two rows the report is about.

**The fix collides with this ticket's own "must NOT" list.** The `Scorer` contract is
`(split, rng) -> frame` (`harness.py:153`), so there is no channel to pass a dataset down to
`fit()` without changing that signature — which means touching `MODEL_REGISTRY` and
`evaluate_model`, both forbidden at line 29 above.

**Option chosen: (a) active-dataset state.** Two module-level paths plus a context manager in
`splits.py`; `load_split`, `split_summary`, `gbdt.build_window_matrix` and `hmm_score.fit` read
from them. `harness.run()` enters the context for the duration of the run. No signature changes
on the scoring path, so the "must NOT" list survives intact.

Rejected: (b) threading the dataset through `Scorer`. Cleaner and free of global state, but it
changes `MODEL_REGISTRY`, `evaluate_model` and both `score_*` signatures — a large diff on the
primary scoring path two days before freeze, and it contradicts this ticket as written.

**Known ceiling of (a), carried in a `ponytail:` comment in the code:** the state is module-level
and therefore neither thread-safe nor nestable across concurrent runs. Upgrade path is (b), if
the harness ever scores datasets in parallel.

**Added to Done when** (the guard the original ticket did not ask for and needs most): a
contamination test that points the override at a modified copy of the parquet pair and asserts
the *fitted* models read the override rather than `data/synthetic/`.
